청소 로봇 아키텍처

Dreame L40 Ultra Gen 2 3대(순정 펌웨어)를 교회 엣지 서버가 Home Assistant(지금은 클라우드 통합, Matter OTA 후 로컬)로 지휘하고, 천장 카메라가 로봇 윗면 AprilTag로 위치를 잽니다. 이 페이지는 전체 구조와 위치 정확도를 다루고, 세부는 소프트웨어·하드웨어 문서로 나눴습니다.

1 · 시스템 경계

누가 무엇을 통해 시스템을 쓰는가

점선 상자는 교회가 통제하지 않는 외부 시스템입니다. 로봇 상태 일부(지도, 청소 면적, 소모품)만 Dreame 클라우드를 거치고, 명령·위치·영상은 교회 안에서 끝납니다.

2 · 계층

도메인 로직은 로봇 종류를 모릅니다

RobotPort 인터페이스 하나로 실제 로봇(DreameAdapter)과 시뮬레이션(SimAdapter)을 바꿔 끼웁니다. Windows 11 Docker에서 검증한 Fleet·Coverage 코드가 현장에서 그대로 돕니다.

3 · 운행 데이터 흐름

3대가 운행하는 동안 장비 사이로 흐르는 신호

왼쪽은 실제 계획대로 움직이는 가상 시뮬레이션이고, 오른쪽은 같은 순간 장비 사이로 오가는 메시지입니다. 로봇 상태는 Wi-Fi → Home Assistant(Matter), 위치는 천장 카메라 → Tracker, 명령은 Fleet Manager → Home Assistant → 로봇 방향으로 흐릅니다.

    5 · AprilTag 위치 오차

    3대 모두 태그를 달면 위치 오차는 95% 기준 약 3–6 cm

    세 로봇 윗면에 서로 다른 번호의 AprilTag(tag36h11, ID 0·1·2)를 붙이고 천장 카메라로 찾는 경우를 계산했습니다. 결론부터 말하면 태그가 보일 때는 3–6 cm(95%), 의자 밑에 들어가 가려지면 카메라로는 잴 수 없어 로봇이 보고하는 위치와 이동 모델로 이어 붙여야 하며 이때는 약 10–30 cm입니다. 벽에 단 카메라 2대로는 먼 곳의 태그가 너무 작아져 검출이 안 됩니다.

    계산 조건 (바꿔 보세요)

    95% 오차2 cm10 cm+ 검출 불가 의자 밑 (가려짐)
    오차 요인 (1축 σ)모델카메라 바로 아래화면 가장자리

    95% 반경 = 2.45 σ (2차원 정규분포). 겹치는 카메라가 있으면 역분산 가중으로 합칩니다. 시간 동기 오차는 로봇 속도 0.3 m/s 기준이며 카메라끼리 공통이라 합쳐도 줄지 않습니다.

    의자 밑에서 태그가 가려질 때

    • 좌석 높이 43–48 cm가 로봇(35 cm)을 완전히 덮어 위에서는 보이지 않습니다. 시뮬레이션 기준 운행 시간의 약 25–35%.
    • 1순위: Home Assistant가 주는 로봇 자체 위치(Dreame 지도 좌표)를 Tk로 변환. 예상 ±7–10 cm.
    • 2순위: 들어간 지점·시각과 나온 지점·시각 사이를 직선 보간, 좌우는 의자 다리 통로(±5 cm)로 제한. 앞뒤 방향 ±15–30 cm.
    • 청소율 계산에는 태그가 보인 구간만 "확정"으로 칠하고, 가려진 구간은 "추정"으로 따로 표시합니다.

    3대를 동시에 추적할 때

    • tag36h11은 해밍 거리 11이라 ID 0·1·2를 서로 잘못 읽을 확률은 사실상 0입니다.
    • 로봇끼리 가장 가까이 오는 곳은 뒷문(폭 1.4 m)과 뒤쪽 통로이며, 교통 관제에 필요한 정확도(±20 cm)보다 10배 여유가 있습니다.
    • 로봇 윗면은 평평해 다른 로봇이 태그를 가리지 않습니다.
    • 태그 방향으로 로봇 진행 방향(헤딩)도 함께 얻습니다. 예상 ±2–4°.
    권장: 천장 높이를 실측한 뒤 위 계산기로 대수를 정합니다. 6 m 이상이면 4K 카메라 4대(2×2) + 10 cm 태그로 바닥 전체를 덮고, 그보다 낮으면 6대(3×2)가 필요합니다. 벽면 카메라 2대 안은 버립니다.
    6 · Valetudo 생태계

    Valetudo를 어떻게 쓰는가: 펌웨어는 못 올리고, 설계는 그대로 따른다

    Valetudo는 루팅한 로봇 안에서 제조사 클라우드를 대신 돌며, 로컬 웹 UI·REST API·MQTT(Homie, Home Assistant 자동 등록)를 제공하는 오픈소스입니다. 공식 지원 목록에는 이름이 정확히 "L40 Ultra"인 1세대만 있고, 우리가 고른 L40 Ultra Gen 2는 없습니다. 그래서 이 프로젝트는 Valetudo를 두 층으로 나눠 씁니다.

    지금 적용 설계와 인터페이스를 빌려 씀

    • RobotPort = Valetudo capability 이름: BasicControl, ZoneCleaning, MapSegmentation, GoToLocation, CombinedVirtualRestrictions, ConsumableMonitoring, AutoEmptyDockManualTrigger, CurrentStatistics를 그대로 메서드로 씀.
    • SimAdapter는 Valetudo처럼 말함: 가상 로봇 3대가 Valetudo와 같은 MQTT(Homie) 토픽 구조로 상태를 내고 명령을 받음. Fleet는 진짜 Valetudo 로봇과 가상 로봇을 구분하지 못함.
    • 지도 교환 형식 = ValetudoMap JSON: 층(바닥·벽·구역)과 엔터티(로봇 위치·충전대·경로·가상 벽·금지 구역) 구조를 내부 지도 형식으로 채택. 관리 페이지와 시뮬레이션이 같은 형식을 그림.
    • 로컬 우선 원칙: 원격 측정 없음, 영상은 교회 밖으로 안 나감. Valetudo의 "로봇은 로컬에서만" 원칙을 카메라·서버에도 적용.

    선택지 로봇을 X40 Ultra로 바꾸면 펌웨어까지 사용

    • X40 Ultra는 지원 목록에 있고 루팅이 "비교적 쉬움", Dreame 브레이크아웃 PCB 권장, 보증 봉인 유지.
    • 로봇마다 Valetudo가 돌고, 엣지 서버의 ValetudoAdapter가 로컬 MQTT·REST로 직접 지휘. Dreame 클라우드도 Home Assistant 통합도 필요 없음.
    • 로봇 자체 위치(robot_position)를 로컬 지도 데이터로 받아 위치 융합의 두 번째 측정으로 사용. 의자 밑에서 태그가 가려질 때 오차가 크게 줆.
    • AutoEmptyDockManualTrigger로 먼지 비움 순서를 서버가 직접 정함 (도크 전원 문제 해결).
    • 비교는 하드웨어 2장.

    위: 현재 경로 (L40 Ultra Gen 2, 순정 펌웨어). 아래: Valetudo 경로 (X40 Ultra 루팅). 두 경로 모두 오른쪽의 같은 RobotPort로 들어가므로 Fleet·Coverage·웹은 바뀌지 않습니다.

    L40 Ultra Gen 2의 현재 제약
    • Dreame 제품 페이지 기준 Matter는 "향후 OTA 업데이트로 제공 예정"입니다. 그 전까지 명령은 Home Assistant dreame_vacuum(클라우드) 또는 앱 일정에 기댑니다.
    • dreame_vacuum 통합의 Gen 2 지원은 미확인입니다. 1대 시험에서 확인합니다.
    • 둘 다 안 되면: 앱 일정으로 출발만 맞추고, 서버는 카메라로 감시·기록만 하는 "관찰 모드"로 축소.
    Valetudo를 쓸 때 지켜야 할 것
    • Valetudo와 제조사 앱은 동시에 쓸 수 없고, 루팅은 사실상 되돌리기 어렵습니다.
    • 지원 목록에 없는 로봇은 지원하지 않습니다. Gen 2·L40 Ultra AE·L40s Pro Ultra, 일부 시장의 "L40" 리배지 모델 문의는 하지 않습니다.
    • Valetudo는 한 로봇당 지도 하나만 지원합니다. 본당은 한 층이라 문제없습니다.
    • Valetudo 자체에는 여러 대 협업 기능이 없습니다. 협업은 우리 Fleet가 맡습니다.
